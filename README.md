# Corporate Admin

Учебная веб-панель корпоративного справочника на Java и Spring Boot. Администратор управляет сотрудниками, отделами и разрешениями ролей через браузер. Тема выбрана так, чтобы показать настройку прав доступа без лишней предметной сложности.

## Возможности

- Вход по логину и паролю; пароли сохраняются как BCrypt-хеши.
- Просмотр сотрудников и отделов, добавление и изменение записей.
- Назначение сотруднику роли и отдела, отключение учетной записи, смена пароля.
- Настройка разрешений ролей `MANAGER` и `VIEWER` через интерфейс.
- Проверка разрешения на сервере при каждом запросе. Изменение прав действует сразу, даже для уже вошедшего пользователя.
- Защищенная роль `ADMIN` и главный администратор, которого нельзя отключить или лишить роли.
- Хранение данных в локальной файловой базе H2.

## Технологии

Java 17+, Spring Boot 4.1.1, Spring MVC, Spring Security, Spring Data JPA, Thymeleaf, H2, Maven.

## Запуск

Нужны Java 17+ и Maven 3.6.3+. В PowerShell:

```powershell
$env:ADMIN_PASSWORD = 'ReplaceWithAStrongPassword123!'
mvn spring-boot:run
```

Откройте [http://localhost:8080](http://localhost:8080). Логин — `admin`, пароль — значение `ADMIN_PASSWORD`. При первом запуске пароль должен содержать минимум 12 символов. Учетная запись создается только один раз: изменение переменной окружения позднее не меняет пароль существующего пользователя. Для смены пароля откройте карточку администратора в панели.

База создается в `data/` рядом с проектом; эта папка исключена из Git. При повторном запуске данные сохраняются. Для чистого демонстрационного запуска остановите приложение и удалите папку `data`.

Проверка проекта:

```powershell
mvn test
```

После публикации на GitHub тот же набор тестов запускается автоматически через GitHub Actions.

## Роли и разрешения

| Разрешение | Действие |
| --- | --- |
| `EMPLOYEE_READ` | просмотр сотрудников |
| `EMPLOYEE_WRITE` | изменение данных сотрудников |
| `DEPARTMENT_READ` | просмотр отделов |
| `DEPARTMENT_WRITE` | добавление и изменение отделов |
| `ROLE_READ` | просмотр ролей |
| `ROLE_WRITE` | настройка разрешений ролей |
| `USER_MANAGE` | создание учетных записей, назначение ролей, блокировка и смена пароля |

При первом запуске создаются роли `ADMIN` (все разрешения), `MANAGER` (просмотр и изменение сотрудников, просмотр отделов) и `VIEWER` (только просмотр сотрудников и отделов). Разрешения ролей `MANAGER` и `VIEWER` можно менять на странице **Роли и права**. Изменять учетные записи позволяет именно `USER_MANAGE`; одного `EMPLOYEE_WRITE` для этого недостаточно.

Роль `ADMIN` нельзя менять через интерфейс. Ее можно назначить только первоначальному администратору. Это сохраняет возможность восстановить доступ после ошибочной настройки других ролей.

## Архитектура

```text
Браузер → Spring Security → PagesController → AdminService → Spring Data Repository → H2
                         ↘ DirectoryFacade → три репозитория чтения → H2
                         ↘ AccessService → AccessPolicy → роль и разрешения в БД
```

Код разделен по ответственности: `model` описывает данные, `repository` отвечает за хранение, `service` — за правила изменения данных, `security` — за проверку доступа, `web` — за HTTP и отображение. `DirectoryFacade` дает контроллеру единый вход для чтения сотрудников, отделов и ролей. Контроллер не содержит SQL и не рассчитывает права из названия роли.

### SOLID

- **S**: `PagesController`, `AdminService`, `DirectoryFacade`, репозитории и классы безопасности имеют разные обязанности.
- **O/D**: `AccessService` зависит от интерфейса `AccessPolicy`; способ принятия решения о доступе можно заменить отдельной реализацией без изменения контроллеров.
- **L**: реализация `RoleAccessPolicy` может использоваться через контракт `AccessPolicy`.
- **I**: `AccessPolicy` содержит один метод, нужный проверке разрешения.

### Паттерны проектирования

- **Builder (порождающий)**: `AppUser.Builder` собирает нового пользователя из обязательных и дополнительных полей. Примеры вызова — в `AdminService` и `BootstrapData`.
- **Facade (структурный)**: `DirectoryFacade` скрывает от `PagesController` три репозитория чтения за одним объектом.
- **Strategy (поведенческий)**: `AccessPolicy` и `RoleAccessPolicy` отделяют правило авторизации от его вызова. Сейчас используется одна реализация политики.
- **Repository**: интерфейсы Spring Data скрывают операции с базой от бизнес-логики.
- **MVC**: контроллеры обрабатывают запросы, модель хранит данные, Thymeleaf формирует страницы.
- **Dependency Injection**: зависимости передаются через конструкторы и собираются Spring.

В перечисленных Java-классах есть короткие комментарии с подсказками для защиты: какой принцип или паттерн показан и как объяснить его своими словами.

## Сценарий демонстрации

1. Войти под администратором и создать отдел.
2. Создать сотрудника с ролью `VIEWER`; войти под ним в другом окне браузера.
3. Показать, что страницы доступны только для чтения и изменение прав возвращает отказ в доступе.
4. Под администратором выдать роли `VIEWER` новое разрешение и повторить действие в уже открытой сессии.
5. Показать `AppUser.Builder`, `DirectoryFacade` и `AccessPolicy` как примеры трех групп паттернов, а также комментарии о SOLID рядом с кодом.

## Ограничения учебного проекта

Для простого локального запуска используется H2 и автоматическое обновление схемы. Для рабочего сервиса потребуются миграции БД, журнал действий, резервное копирование и отдельная настройка развертывания. Публиковать реальные пароли и файл базы в репозитории нельзя.
